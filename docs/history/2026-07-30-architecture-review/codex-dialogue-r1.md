2. **[DISPUTE — factual and architectural] The OAuth loser cannot currently clobber the winner on the stated `invalid_grant` path, and CAS-after-refresh is not sufficient.**  
   A failed refresh throws at [`oauth.ts:141-146`](/Users/malo/Code/x-threaded/src/server/oauth.ts:141), before the blind write at [`oauth.ts:185-186`](/Users/malo/Code/x-threaded/src/server/oauth.ts:185); that loser fails its request but does not overwrite anything. More importantly, `UPDATE … WHERE refresh_token = old` after talking to X cannot prevent two isolates from presenting the same single-use token. The durable coordination point must precede the external call: a D1 conditional lease/claim, followed by refresh and replacement; losers wait and reread. In-process single-flight is only an optimization. The unavoidable exchange→persistence crash window should produce an explicit broken/reauthorize state.  
   **Would change my mind:** provider documentation guaranteeing idempotent concurrent refreshes, or a deployment architecture guaranteeing a single serialized refresh actor.
